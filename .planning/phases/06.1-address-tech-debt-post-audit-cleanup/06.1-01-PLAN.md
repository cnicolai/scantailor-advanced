## Conventions for every plan of this phase

Later plans refer to this section as "06.1-01 conventions" and repeat the items their tasks need.

1. Every command runs from the repository root; every path in a plan is relative to it.
2. Scratch files go to `build/scratch/` (gitignored), never `/tmp` or anywhere outside the project. Write files with the Write tool; never run a bare `cat > file` (it blocks on stdin). macOS bash 3.2 cannot parse a quoted heredoc inside `< <(...)`: put helper scripts in their own file. Python runs as `python3 -I`, standard library only (no numpy, no PIL).
3. Nothing outside the project is opened, listed or written by you. Never touch `~/.config/scantailor-advanced/`, `~/Library/...`, OmniFocus or Google Chrome in any form. Build tools and programs built from this checkout may read `/opt/homebrew` and the Xcode / Command Line Tools installation (the user's approval for Phase 06.1: `.planning/phases/06.1-address-tech-debt-post-audit-cleanup/records/access-approval.md`; it already exists, do not rewrite it); do not open files there yourself. Anything else outside the project, including the home folder, needs its own yes (the record's "Not covered" list). Never launch `build/<preset>/scantailor-advanced` (D-00e). No live `mac_check` or `retina_check` run (D-00b, D-09): if a task seems to need one, stop at a checkpoint and ask. Stored user settings are neither read differently, deleted nor rewritten (D-00c).
4. Formatting: run `xcrun clang-format -i <file>` on every C++ file you touch (`.cpp`, `.h`, `.mm`) and check with `xcrun clang-format --dry-run -Werror <file>`. Exception: `src/dewarping/TextLineTracer.cpp` keeps two older violations; never run `-i` on it, edit it with the Edit tool only, and check that `xcrun clang-format --dry-run src/dewarping/TextLineTracer.cpp 2>&1 | grep -c 'warning:'` still prints 2. `.ui`, CMake, JSON, Markdown and Python files are not formatted.
5. Code style (`.claude/CLAUDE.md`): C++17 only; new source files start with the two-line copyright header every existing file carries; include guards `SCANTAILOR_<MODULE>_<NAME>_H_` (check the module token of a neighbouring header), `TST_<NAME>_QT_H` in `src/qt_tests`; no `#pragma once`; `m_` prefix for members; `const` wherever possible; one parameter per line when a list wraps; module headers by bare name; no new `qDebug`/`qWarning` in application code; user-visible strings stay in `tr()` or `QCoreApplication::translate`, English only (D-00d); no raw `new` except Qt objects handed to a parent. Comments carry no planning ID (D-05, widened to every family by the orchestrator): no decision, review-finding, finding-code, requirement, backlog, wave or plan number, no `RESEARCH`/`UI-SPEC` reference and no bare `records/<name>.md`; state the reason in plain words; a full repository path to an existing file may stay. The patterns, the allowlist of five XFAIL tag strings and the checks are in `06.1-09-PLAN.md`, section "D-05 rules for plans 06.1-09 to 06.1-11"; 06.1-15 runs them tree-wide, so a plan after 06.1-11 that adds such a comment fails the closing check.

Every commit that changes a gate input (`src`, `CMakeLists.txt`, `CMakePresets.json`, `cmake`, `config.h.in`, `version.h.in`) passes `bash .planning/phases/03-qt-6-and-macos-only/gate.sh check <label>` on that commit, run right after the commit and before any other commit. Commit first, then gate (the gate refuses uncommitted input changes). When the gate fails, fix the cause, `git commit --amend` (same subject) and rerun with the same label until `result: PASS`. The gate configures, builds every target and runs Release and Debug ctest; it takes 6 to 10 minutes, longer after a CMake change (full rebuild). Start it with the Bash tool in the background (`run_in_background`), wait for its completion notification (do not poll, do not use `pgrep`), then read `build/scratch/gate/<label>/summary.txt`.
