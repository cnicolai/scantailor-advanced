### Advisory: findings of the phase's own code review (recorded after plan 06.1-12's closing check)

`06.1-REVIEW.md` (0 critical, 1 warning, 4 info) and `06.1-REVIEW-DISPOSITION.md` (5 rows `open`, `open: 5`). These are findings about 06.1 itself, outside the six files named in the goal, so they do not fail the goal. They stay as follow-up for the next review cycle.

- **WR-01 (own-file ceiling versus very large outputs): does not contradict a must-have.** The reviewer's premise is that the Change-DPI dialog accepts custom dpi up to 9999. The validator does allow 0 to 9999, but the submit handler refuses anything outside 72 to 1200 (`ChangeDpiDialog.cpp:92-99`: "DPI is too low!" / "DPI is too high!"), and the default-parameters dialog lists dpi up to 1200 only. At the maximum UI-reachable 1200 dpi, an A3 page is about 278 Mpx and a 500 mm square about 558 Mpx, both under 2^30 - 1 px, so the 06.1-06 must-have ("derived from the largest output the app can write ... so a file the app wrote is never refused") holds for every value the UI can set. The reviewer's A3-at-2400-dpi case can only arise from a hand-edited project file; there the page would regenerate on each visit (a performance cost, not a data loss or crash). Suggested follow-up, low priority: one sentence in `ImageSizeLimit.h` and `ImageLoader.h` stating that the ceiling assumes the 1200 dpi UI limit.
- IN-01 to IN-04 (a control in `testHarnessMainsUseTheGuard` that cannot fail, `homeRedirected` comparing a canonical path with non-canonical ones, `exceedsOwnFile` duplicating `exceeds`, the page-cache test not failing against the current container): test-hygiene or style items with no output effect.
