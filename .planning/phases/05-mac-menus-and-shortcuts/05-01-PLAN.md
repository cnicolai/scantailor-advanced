## Conventions for every plan of this phase

Later plans refer to this section and repeat the items their tasks need.

1. Every command runs from the repository root; every path in a plan is relative to it.
2. Scratch files go to `build/scratch/` (gitignored), never `/tmp` or anywhere outside the project. Write files with the Write tool; never run a bare `cat > file` (it blocks on stdin). macOS bash 3.2 cannot parse a quoted heredoc inside `< <(...)`: put helper scripts in their own file under `build/scratch/`.
3. Nothing outside the project is opened, listed or written by you. Never touch `~/.config/scantailor-advanced/`, `~/Library/...` or OmniFocus. Build tools and the programs built from this checkout may read `/opt/homebrew` and the Xcode / Command Line Tools installation (approved for Phases 3 to 6 in `.planning/phases/02-golden-baselines/records/access-approval.md`); do not open files there yourself. Never launch `build/<preset>/scantailor-advanced`: it reads and writes the user's settings under `~/.config` and `~/Library`. `qt_tests` and the live harness `mac_check` (plan 05-02) stand in for it.
4. Formatting: `clang-format` is not on PATH. Run `xcrun clang-format -i <file>` on every C++ and Objective-C++ file you touch and check with `xcrun clang-format --dry-run -Werror <file>`. `.ui` files are not formatted. Never reformat `src/dewarping/TextLineTracer.cpp`.

Code style (`.claude/CLAUDE.md`): C++17 only; new files start with the two-line copyright header of `src/qt_tests/tst_hidpi_qt.h`; `qt_tests` headers use the guard `TST_<NAME>_QT_H`; no `#pragma once`; `m_` prefix for members; `const` wherever possible; one parameter per line when a list wraps; module headers are included by bare name; no new `qDebug`/`qWarning` in application code; user-visible strings stay in `tr()` or `.ui` text; no raw `new` except Qt objects handed to a parent.
6. Key sequences in code and tests are explicit: `QKeySequence(Qt::CTRL | Qt::Key_Comma)`, not `QKeySequence::Preferences`. On the offscreen platform `QKeySequence::Preferences` and `QKeySequence::Quit` are empty (RESEARCH Pitfall 5); only the live harness compares with the Cocoa StandardKey bindings. 7. Tests and the code they cover land in the same commit. Every commit must pass the gate (D-00a), so there is no failing-test commit and no RED/GREEN split.

## Reconciliations (CONTEXT / UI-SPEC versus research)

- UI-SPEC names `QKeySequence::Preferences`, `QKeySequence::Quit` and `QKeySequence::SaveAs` as the shortcuts. This plan sets the explicit sequences `Ctrl+,`, `Ctrl+Q` and `Ctrl+Shift+S` instead (RESEARCH Pitfall 5): they are what those StandardKeys resolve to on Cocoa, and the offscreen tests can only assert explicit sequences. Plan 05-02's harness proves the equality on Cocoa.
- UI-SPEC keeps `actionQuit` "declared in File"; File must not end on an orphan separator after the roles move Settings and Quit. The separator before Quit is therefore removed and `actionSettings` sits between Close Project and Quit (RESEARCH Open Question 4).
- The empty Help menu stays in the `.ui` as UI-SPEC chooses; the tests do not require it, and plan 05-02 measures whether macOS shows it.
