## Decisions recorded by this plan (research open question 3, CONTEXT discretion)

- **Ceiling (D-01, research open question 3; corrected at plan revision):** a page must have fewer than 2^29 px in total, written as the inclusive maximum `kMaxPixels = 2^29 - 1 = 536870911`, and at most `kMaxSide = 65535` px per side. Why below 2^29 and not at it: an image of exactly 2^29 px takes 2^31 bytes as RGB32, one byte more than INT_MAX, so an `int` byte count would overflow at the boundary itself (the earlier wording "2^29 keeps RGB32 byte counts below 2^31" was false for an inclusive 2^29). With fewer than 2^29 px, every pixel count of a loaded source image stays below 2^29 (RESEARCH Pitfall 4 sites) and its RGB32 byte count is at most 2147483644, which a `static_assert` in `ImageSizeLimit.h` pins. This bounds the source image as loaded; images derived later (deskew rotation, output dpi scaling) are sized by the user's settings, not by this limit, and are outside SAFE-01. 536870911 is 1.93 times the 1200 dpi A3 reference page (278417133 px), which D-01 says must load. RESEARCH assumption A2 (byte-count sites not audited) is closed by a bounded audit of the `int` pixel, element and byte counts reachable for a loaded source image in plan 06-06, recorded in `records/safe-01.md`. The user's "1 gigapixel" was an example of the intended size; fewer than 2^30 px would keep pixel counts below 2^31 but let an RGB32 byte count reach 2^32 - 4, so it is safe only if that audit finds no `int` byte count; plan 06-06 records the comparison. One constant, reversible.
- **Qt reader limit (D-03):** `QImageReader::setAllocationLimit(2048)`: 2048 MB is the smallest whole number of megabytes that holds the largest accepted RGB32 image (4 x 536870911 bytes = 2047.99 MB; Qt accepts an image whose byte size is at most the limit), so Qt never refuses an image this limit accepts. Set once inside `ImageLoader`. Never 0. This plan only defines the constant `kQtAllocationLimitMb`; plan 06-05 applies it.
- **Size semantics:** header sizes are unsigned 32-bit values carried in `int`; a negative side therefore means a header value of 2^31 or more and counts as "too large", and texts print sides as unsigned. A side of 0 is not "too large"; the reader still refuses it with a null image instead of throwing `std::bad_alloc` as it does today, and the page view then shows the generic "could not be loaded" text.
- **Message wording (CONTEXT discretion):** page view: `The following file is too large to load:\n<path>\n\nIts image size is <W> × <H> px. The limit is 65535 px per side and 537 megapixels in total.`; short form for lists: `too large: <W> × <H> px` (used by plan 06-06). `×` is U+00D7. Numbers are plain digits (no locale grouping), so tests do not depend on the locale.
