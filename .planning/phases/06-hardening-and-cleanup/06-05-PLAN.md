## Decisions this plan applies (recorded in plan 06-04)

- **Qt reader limit (D-03):** `QImageReader::setAllocationLimit(ImageSizeLimit::kQtAllocationLimitMb)` (2048 MB, the smallest whole number of megabytes that holds the largest accepted RGB32 image of 4 x 536870911 bytes, so Qt never refuses an image the project limit accepts), set once inside `ImageLoader` through `std::call_once`. Never 0: with 0 Qt allocates an image of the claimed size before failing (RESEARCH D-03 table).
- **Message wording:** the page view uses the same `LoadFileTask` text as for TIFF (plan 06-04), so PNG and JPEG need no new string.

## Decision recorded by this plan (checker revision, D-04)

- **PNG metadata path:** `PngMetadataLoader` gets no early return of its own, unlike `JpegMetadataLoader`: it calls only `png_read_info`, which allocates nothing in proportion to the claimed size, and like the TIFF loader it reports `LOADED` with the claimed size, so the one consumer check (`ImageSizeLimit::claimedSizeIfTooLarge` in the page view, `oversizedPagesText` at project creation and insertion, plan 06-06) gives the same verdict for all three formats. The one place where the PNG verdict differed is closed: libpng refuses a header with a side above its default user limit (1000000 px; `png_error`, so the loader returned `GENERIC_ERROR` and the user saw "could not be loaded"); `png_set_user_limits(png.handle(), PNG_UINT_31_MAX, PNG_UINT_31_MAX)` before `png_read_info` makes it report the claimed size, and the size check then names the file too large. Observed first on the unmodified loader and recorded in the SUMMARY.
