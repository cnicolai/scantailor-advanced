## Decisions recorded by this plan (CONTEXT discretion, research open question 1)

- **Budget share:** half of `hw.memsize` (the rest stays with macOS, the GUI, the thumbnail cache and compressed memory). On this Mac 68719476736 B gives a budget of 34359738368 B.
- **Factor:** 40 B per pixel of the larger of source and estimated output pixel count, 1.2 times the worst measured 33.1 B (RESEARCH "Memory model, measured"; harness numbers, confirmed against the probes in plan 06-16).
- **Estimator rule (open question 1):** the fixed rule `max(srcPx, ceil((w x 600 / dpiX) x (h x 600 / dpiY)))` with 600 = the app's default output dpi; no accessor into `output::Settings` and no coupling to the output filter. It under-estimates only if the user sets an output dpi above 600, by (outDpi / 600)^2; revisit then. (Research open question 1 is resolved with this rule.)
- **When the cap is set:** at every `startBatchProcessing` (the loop over all pages is already there); `updateNumberOfThreads` runs on every `submitTask` and only applies the stored cap. The cap stays in force for interactive processing after a batch, which runs one page at a time anyway.
- **One cap function:** `MemoryBudget::batchMemoryCap(const PageSequence&)` is the only place that combines RAM and page sizes into the cap. `startBatchProcessing` calls it, and so does the D-08 batch probe of plan 06-09, so the memory run of plan 06-16 exercises exactly the app's cap.
- **D-08 run page (pinned here as a test vector):** 12000 x 13800 px at 3600 dpi (the probe's MIXED page at 1200 dpi scaled by 3), 165600000 px, estimate 40 x 165600000 B = 6317 MiB; cap 5 on this Mac's 64 GiB (below its idealThreadCount of 10) and 1 on 16 GiB.
